# Лабораторная работа №3

## Тема

**Разработка модульных тестов для Django-приложения**

## Постановка задачи

В рамках лабораторной работы №3 необходимо разработать набор автоматизированных тестов для Django-приложения интернет-магазина, созданного в рамках лабораторной работы №2.

Основная цель работы — проверить корректность работы моделей, бизнес-логики и представлений приложения с помощью модульных тестов.

В проекте особое внимание уделено тестированию:

- создания и хранения объектов моделей;
- связей между моделями;
- методов расчета исторической суммы покупок (`Customer.total_spent()`);
- расчёта скидки по общей стоимости товаров в текущей корзине;
- расчёта суммы скидки и итоговой стоимости заказа;
- корректности работы представлений;
- формирования HTTP-ответов;
- операций с корзиной, хранящейся в сессии;
- создания объектов через POST-запросы;
- обработки граничных значений скидки;
- поведения приложения при повторных покупках и оформлении заказа;
- корректности URL-маршрутов.

## Краткое описание проекта

В качестве основы используется Django-приложение магазина, разработанное в рамках лабораторной работы №2.

Приложение работает с тремя основными сущностями:

- **Product** — товар с названием и ценой;
- **Customer** — покупатель с именем и адресом;
- **Purchase** — покупка, связывающая покупателя с товаром и содержащая дату создания.

Главная страница отображает каталог товаров и список покупателей, а также текущую корзину пользователя. Корзина хранится в сессии. Пользователь может добавлять товары в корзину и удалять их. Один и тот же товар можно добавить несколько раз.

Перед оформлением заказа пользователь выбирает существующего покупателя или создаёт нового. После подтверждения заказа для каждого товара из корзины создаётся отдельная запись `Purchase`. Создание записей выполняется в транзакции, после чего корзина очищается.

Скидка рассчитывается по общей стоимости товаров в текущей корзине, а не по истории предыдущих покупок:

| Сумма товаров в корзине | Скидка |
| ----------------------- | ------ |
| менее 5 000 ₽           | 0%     |
| от 5 000 ₽              | 3%     |
| от 10 000 ₽             | 5%     |
| от 20 000 ₽             | 10%    |

Метод `Customer.total_spent()` возвращает историческую сумму покупок покупателя. Эта величина не используется для определения скидки на текущий заказ.

Лабораторная работа №3 сосредоточена на проверке этой логики и поведения приложения с помощью автоматизированных тестов.

## Организация модульных тестов

### `test_models.py`

В файле `test_models.py` реализованы тестовые классы:

- `ProductTestCase`;
- `CustomerTestCase`;
- `PurchaseTestCase`.

Каждый тестовый класс наследуется от `django.test.TestCase`.

Для подготовки исходных данных используется метод `setUp()`, в котором создаются необходимые объекты базы данных.

### `test_views.py`

В файле `test_views.py` реализованы тестовые классы:

- `IndexViewTestCase`;
- `PurchaseCreateViewTestCase`;
- `CustomerCreateViewTestCase`.

Для проверки HTTP-взаимодействия используется стандартный Django Test Client через `self.client`.

### `test_urls.py`

В файле `test_urls.py` реализован тестовый класс `UrlsTestCase`, который проверяет соответствие URL-маршрутов представлениям с помощью `django.urls.resolve`.

## Реализуемая бизнес-логика и её тестирование

Основные вычисления, связанные с корзиной, выполняются по общей стоимости товаров в текущей корзине.

Размер скидки определяется по сумме текущей корзины:

```python
def get_discount_percent(total):
    if total >= 20000:
        return 10
    if total >= 10000:
        return 5
    if total >= 5000:
        return 3
    return 0
```

Сумма скидки:

```python
discount_amount = total * discount_percent / 100
```

Итоговая стоимость:

```python
total_with_discount = total - discount_amount
```

Метод `Customer.total_spent()` вычисляет историческую сумму покупок и не участвует в расчёте скидки на текущий заказ:

```python
def total_spent(self):
    return sum(
        purchase.product.price
        for purchase in self.purchases.select_related('product').all()
    )
```

Все перечисленные методы и функции покрыты автоматизированными тестами. Проверяется как каждая отдельная функция бизнес-логики, так и их совместная работа при оформлении заказа.

## Принцип работы тестовой базы данных

При запуске тестов Django автоматически создаёт отдельную тестовую базу данных.

Тесты выполняются изолированно от основной базы данных, а после завершения тестирования тестовая база удаляется.

Это позволяет:

- создавать тестовые объекты непосредственно во время выполнения тестов;
- проверять создание, изменение и удаление данных;
- не изменять рабочие данные приложения.

Подготовка тестовых данных выполняется в `setUp()` каждого тестового класса.
